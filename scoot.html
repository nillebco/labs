Scoot, forked

Pagecast makes a web page searchable: press ⌥. and type what you want. This is the same question asked of the whole desktop — can the macOS accessibility tree carry a palette the way the DOM does? — built on Scoot, a BSD-3 keyboard cursor actuator.

⇧⌘J scan→ ⌨️ type→ 🎯 filter→ ↵ press

The palette half does not exist yet. What exists is the matcher, the instruments used to measure the tree, and the bugs those instruments found. This page is a log, not a download.

Why fork Scoot

  • The alternatives are closed. The only palette-shaped tool for the Mac's own interface is Shortcat (free, still 0.x, last release July 2025); Homerow and Paletro are commercial. The two open-source projects — Vimac (GPL-3.0, dead since 2022) and Scoot (BSD-3, maintained) — both do hint labels and a grid, not search.
  • Scoot already has the hard parts. A transparent overlay per display that joins all Spaces, correct across multiple monitors, click and drag synthesis, a menu bar agent, global hotkeys. Everything except the query.
  • BSD-3 keeps the options open: the result can be closed, sold, or shipped on the App Store — which a GPL fork could not.

What is in the fork

  • A fuzzy matcher (Scoot/Fuzzy.swift): whitespace-separated tokens that must all match, subsequence matching, and bonuses for a match at the start of the string, at a word boundary (separator or camelCase hump) and inside a consecutive run. It returns the matched ranges, so a list can highlight them. Pure Swift, no AppKit, 19 tests.
  • A dump of what the tree exposes: every element of the focused window with role, title, description, value, identifier and frame, plus a count per role and how many elements carry no text at all. It answers “which text could a palette rank?” for a given app, before any palette UI exists.
  • Its own Accessibility identity: bundle id co.nillebco.scoot, signed so the TCC grant survives rebuilds, living beside a Homebrew-installed Scoot.

What using it taught

Four bugs, all found by measuring instead of reading:

  • Zen showed browser chrome, not the page. Firefox exposes the document as an AXWebArea that reports no frame of its own, and Scoot skipped the whole subtree of any node without a frame. Descending anyway: 17 elements → 82 on the same window, 38 of them links.
  • Firefox keeps its tree shut until asked. With AXEnhancedUserInterface off, Zen exposes 6 nodes and 3 buttons with no title; with it on, 1674 nodes and 164 actionable ones — after about two seconds of waking up. The flag is now switched on at invoke, and the scan retries while the tree fills in.
  • The labels outlived the overlay. They live in borderless windows that join every Space, and hiding them relied on windowDidResignMain — which does not fire when a menu bar agent is hidden. A stranded overlay survived a whole night; it is now ordered out explicitly.
  • Two ways to “crash” without a crash. ⌘Q reached the main menu and quit the agent instead of dismissing the overlay, and a leftover pkill in the test script SIGTERM-ed the running app on every test run. Both look identical on screen; the exit status in the log tells them apart.

What is next

  • Keep the AXUIElement handle in the model: today Scoot throws it away and clicks a rectangle, so nothing can be activated with AXPress.
  • A palette view — query field, ranked rows, arrow keys, Enter. The matcher is already written.
  • Menu bar traversal, which is how Shortcat and Raycast search an app's menu items for very little work.
  • Plugins keyed by bundle id: the piece Pagecast has and none of the Mac tools do.

Status, honestly

An experiment, not a product: no release, no download, and element mode is still the upstream decision tree. What exists is committed and tested — 45 unit tests — on GitHub, forked from mjrusso/scoot under BSD-3-Clause.
